# Community go-live checklist (user steps)

Nothing here is done by the assistant. Never paste a secret in chat, a commit or an issue. Background: README section 3f. Payments checklist: `docs/payments-go-live-checklist.md`.

1. **Upload the roster (bulk method, optional).** The branch chair, counselor or officers can export the branch member list from IEEE vTools. Save it as CSV with columns for member number (8 or 9 digits; 7 digits get a leading zero. IEEE member numbers are 8 or 9 digits (for example 01234567 or 101809133). The IEEE Membership Validator accepts the number as shown on your IEEE card or account.), expiry date (YYYY-MM-DD, DD/MM/YYYY or DD-Mon-YYYY) and optionally name (header row optional; max 5 000 rows). Open `/admin/membership` -> Roster -> choose the file, check the preview, upload. Without names every claim goes to manual review.
2. **Add `COMMUNITY_HASH_SALT`.** Cloudflare -> Workers & Pages -> stairway -> Settings -> Variables and Secrets -> type **Secret**, 16+ random characters (or `npx wrangler secret put COMMUNITY_HASH_SALT`). Without it the per-IP form limit is off.
3. **Optional AI pre-screen.** Add the **Secret** `ANTHROPIC_API_KEY`, then add `IEEE_PRESCREEN_ENABLED` = `true` as a **Secret** too (plain dashboard variables are dropped on the next deploy), and optionally `IEEE_PRESCREEN_MODEL`. Set a monthly spend limit in the Anthropic console. Leave it off to use roster + manual review only. It is a hint; a human still approves.
4. **Test each home form** at `/#get-involved` (host an event, partner, feedback incl. one anonymous). Confirm each appears in `/admin/requests`, change a status, download the CSV, then confirm a 6th submission in a day from the same email is refused.
5. **Test chat with two accounts.** A verified member (always eligible) and an attendee with a confirmed registration for a published session. Messages must arrive live both ways without refresh; cut the network briefly and see polling resume. Close, flag, block and unblock from `/admin/chat`. A signed-in user with neither sees the "not available" notice. After the session end time the attendee loses chat access.
6. **Test claim flows** with a second Google account: (a) a roster number that matches -> auto-verified, badge on `/me` and `/u/<handle>`; (b) a number that is not on the roster, no photo -> "A branch officer confirms your membership in IEEE's Membership Validator; this usually takes a day", the claim appears in the review queue, then do the Validator review (step 7) and approve; reject another with a reason; (c) the classmate case: claim a number already held by another account -> it asks for a photo and then goes to review, never a hint about who holds it. Approve with a date within 30 days to see the renewal prompt and the "Show expiring in 30 days" filter; revoke.
7. **Review a claim with the IEEE Membership Validator** (an officer with Validator access; student branch officers have it automatically). In `/admin/membership` click **Open IEEE Membership Validator** (new tab; sign in with your IEEE account), search by the **member number** (8 characters, leading zeros, use **Copy member number**) or by the member's **primary email** (shown on the card). Read: **status must be Active**, the **grade**, and the **expiry date**. Back in the app tick **I confirmed active membership in the IEEE Membership Validator**, enter that expiry date and approve. If the status is not Active or the person is not found, reject with a reason. Do not share Validator results outside the review; the app stores only the expiry date and a yes/no confirmation in the audit log.
8. **Optional, later: IEEE Membership Validator API.** IEEE offers a programmatic API only to IEEE-approved conference registration systems. If the branch ever wants it, apply at https://forms.vtools.ieee.org/membership-api/ (IEEE Meeting & Events Planning approves; valid up to 1 year; roughly 2 weeks of review). The current flow does not need it.
9. **Live-only verifications** that cannot run offline: Realtime push end-to-end with RLS (another user's or an ineligible tab receives nothing), signed upload enforcement for the `ieee-proof` bucket (cannot write another user's path, a wrong type or over 5 MB), real response headers (`/me/*` and `/admin/*` redirect when signed out; `/robots.txt` disallows `/me/` and `/admin/`; the sitemap lacks the new routes).
10. **Retention:** the purge runs from the cron tick only while payments or sync are on. Until then run `select private.purge_community();` monthly in the Supabase SQL editor and delete the returned `proof_paths` in Storage -> `ieee-proof`.
11. **Reminder:** email notifications stay off until a sending domain exists; Workers **Paid** is still recommended (10 ms CPU on Free).
